# Meeting Agent · 智能会议纪要

把一场会议的音频变成**可追溯、可执行的结构化纪要**。

上传录音或会中直接录音，系统自动完成语音转写、说话人分离、内容理解，最终产出带责任人和截止时间的决议、待办与风险清单。**每一条结论都能点击跳回原话**。

---

## 这个项目能做什么

### 1. 把音频变成文字

| 能力 | 说明 |
|---|---|
| **离线转写** | 上传音频文件，整段转写成带时间戳的文字 |
| **实时转写** | 会议进行中边说话边出字，延迟 1~2 秒 |
| **说话人分离** | 自动区分「有几个不同的人在说话」，标注为说话人 A / B / C |
| **说话人命名** | 点击说话人姓名即可标注真实身份，标注后全场同步更新 |
| **自动格式转换** | 任意采样率、声道数的音频自动规整成识别服务要求的格式，无需手动转码 |

支持的音频格式：`wav` `mp3` `m4a` `flac` `webm` `ogg` `opus` 等。

### 2. 把文字变成纪要

系统会从转写内容中自动提取：

- **会议概述** —— 3~5 句话总结达成了什么结论
- **决议** —— 会上明确拍板的事项
- **待办** —— 具体行动项，含责任人与截止时间
- **风险** —— 可能影响交付的问题，标注严重程度

### 3. 每条结论都能回溯原话

这是本项目的核心设计。纪要里每一条内容都可以点击「引用」，页面会跳转到对应的那句原话并高亮显示。

意义在于：**纪要出错时能立刻定位到是转录错了，还是理解错了。**

### 4. 按会议类型调整抽取规则

不同会议关心的内容不一样，系统内置三种「会议类型」（Skill），新建会议时可选：

| 类型 | 适用场景 | 抽取重点 |
|---|---|---|
| **标准会议纪要** | 对齐会、讨论会、跨部门同步 | 拍板决定、有负责人的待办、影响交付的风险 |
| **研发周会** | Scrum 站会、迭代同步 | 已完成产出、阻塞项、下周计划 |
| **客户沟通会** | 需求沟通、方案评审 | 客户诉求、我方承诺、商务风险 |

类型不同，抽取的侧重点和输出风格都不同。例如研发周会会特别指出「阻塞情况是否明确」。

### 5. 跨会议追问

可以就历史会议内容提问，例如：

> 「上次关于排期定了什么？」

系统会检索历史纪要与记忆，给出**带引用来源**的答案。**查不到时会明确说「没找到」，不会编造。**

### 5.5 会议中实时提问

开着会随口就能问，不用等会议结束、也不用重新上传音频：

> 「刚才说了什么？」
> 「谁负责联调环境？」
> 「到现在定了哪些事？」

回答只依据**本场会议已经转写出来的内容**和**往期会议沉淀的记忆**，并且：

- **跟得上最新一句**：提问时会把「还在识别中」的文字一起带上，不用等它落库
- **能整体概括**：问「总结一下会议」「会上讲了什么」时，会通读整场转写给出概括；内容零散（如试音）会如实说明，不硬凑结论
- **能按人问**：问「对方说了什么」「我说了什么」「张伟说了什么」时，只在那个人的发言里回答，不会把别人的话算到他头上
- **记得以前的会**：本场没说过、但以前定过的事，会从往期记忆里找出来回答，并明确标注「之前 / 上次」和来源会议
- **带出处**：每条依据都有时间点与说话人，可以展开对照原话；往期记忆单独分区展示，不和本场发言混在一起
- **不编造**：两边都没有的，直接回答「会上还没有提到」
- **边说边出**：答案逐字流式返回，先拿到出处再等正文；觉得答偏了随时点「停止」
- **不会卡住**：模型超时或不可用时，自动用本地检索把相关原话摆出来，而不是报错

入口在实时会议页底部的「会中提问」卡片，`Enter` 直接发送。

记忆的取用有三条硬规则：**已过时、有冲突、已遗忘的记忆不参与**；
**与本场结论冲突时以本场为准**；**问「刚才」时不会冒出上个月的内容**。

两者的区别：**跨会议追问**查的是历史纪要与记忆；**会中提问**以本场正在产生的转写为主，
并把往期记忆作为背景知识补充。

### 6. 记忆管理

会议产生的结论不会用完即弃，而是沉淀为**长期记忆**，可以在「记忆管理」页面查看与维护。

记忆分为四类：

| 分类 | 含义 | 来源 |
|---|---|---|
| **决议** | 会上拍板的事项 | 会议自动沉淀 |
| **未闭环** | 尚未解决的风险或待跟进事项 | 会议自动沉淀 |
| **事实** | 客观信息 | 手动添加 / 历史导入 |
| **经验** | 可复用的做法或教训 | 手动添加 |

每条记忆有独立状态，可以被质疑和淘汰：

| 状态 | 含义 |
|---|---|
| **生效中** | 正常参与检索 |
| **待确认** | 存疑，等人工判断 |
| **有冲突** | 与其他记忆矛盾 |
| **已过时** | 被新结论取代，保留但不再引用 |
| **已遗忘** | 软删除，可随时恢复 |

这个设计的价值在于：**上周决定「先做 A」、本周改成「做 B」时，A 不会被清空，而是标记为「已过时」**。历史可追溯，但不会误导当前判断。

管理页面支持：

- 按分类、状态筛选，支持关键词搜索
- 编辑内容与分类
- 标记「已过时 / 有冲突 / 待确认」
- 遗忘与恢复
- 查看变更记录（谁在什么时候改了什么）
- 跳转到来源会议

### 7. 多人协作与权限

三层权限控制：

```
路由守卫（能不能进这个页面）
    ↓
工具闸门（能不能调用这个能力）
    ↓
数据过滤（只能看到自己租户的数据）
```

三种角色：

| 角色 | 创建会议 | 触发 Agent | 编辑纪要 | 删除会议 | 记忆管理 |
|---|---|---|---|---|---|
| owner | ✅ | ✅ | ✅ | ✅ | ✅ |
| member | ✅ | ✅ | ✅ | ❌ | ✅ |
| viewer | ❌ | ❌ | ❌ | ❌ | ❌ |

删除会议是不可逆操作，所以只给 owner。删除会连带清掉转写、纪要、说话人和实时记录，
但**由这场会沉淀的记忆会保留**（只解除关联），删除动作本身也会写入审计。

### 8. 可观测的运行过程

Agent 的每一步都可见：当前处于哪个阶段、调用了哪些工具、模型输出了什么、每个阶段耗时多久。出问题时能直接定位到具体环节。

### 9. 音频链路诊断

实时录音出问题时，会议详情页的「音频链路诊断」可以逐环检查：

```
麦克风权限   → 已授权
AudioContext → running / 16000Hz
AudioWorklet → 已加载
WebSocket    → 已连接
识别服务     → 就绪
```

同时显示实时音量条、音频帧数与累计时长。音量条不动会明确提示「麦克风可能被静音或选错输入设备」，不用靠猜。


## 功能演示路径

### 路径一：上传音频生成纪要

1. 用 `owner@demo.dev` 登录
2. 首页点「新建会议」，填写标题，选择一个会议类型
3. 上传一段会议音频（或使用演示数据）
4. 进入会议详情，点「生成纪要」
5. 观察运行视图中的阶段推进
6. 在转写区点击说话人姓名旁的铅笔图标，标注真实身份
7. 查看生成的决议 / 待办 / 风险
8. 点击任意条目的「引用」，验证能跳回原话

### 路径二：实时会议

1. 打开任意会议，点右上角「实时模式」
2. 先点「开始诊断」，确认麦克风音量条能随说话跳动
3. 点「开始实时会议」，允许麦克风权限
4. 对着麦克风说话，观察实时转写
5. 边说边在页面下方的「会中提问」里问「刚才说了什么」，验证回答带时间与说话人
6. 再问一个会里没提过的事（例如「有没有讨论预算」），确认它回答「会上还没有提到」
7. 点「结束并生成纪要」

1. 侧边栏点「记忆管理」
2. 按分类筛选（决议 / 未闭环 / 事实 / 经验）
3. 点任意一条查看详情，可以看到来源会议与变更记录
4. 试着把一条标记为「已过时」，再按状态筛选查看
5. 点「遗忘」后用「已遗忘」筛选，可以恢复

## 配置说明

项目支持**完全离线运行**，不配置任何外部服务也能演示全部流程（使用预置数据与本地模型）。

要接入真实能力，按下表配置 `.env`：

### 大模型（生成纪要）

| 变量 | 说明 |
|---|---|
| `MOCK_LLM` | `1` = 使用本地模拟（离线可用）；`0` = 调用真实模型 |
| `LLM_BASE_URL` | OpenAI 兼容接口地址 |
| `LLM_API_KEY` | 接口密钥 |
| `LLM_MODEL` | 模型名称 |

已验证可用的服务：DeepSeek、通义千问、Kimi、任何 OpenAI 兼容网关。

### 语音识别（转写）

| 变量 | 说明 |
|---|---|
| `ASR_PROVIDER` | `mock`（预置数据） / `qwen`（推荐） / `dashscope` / `real` |
| `DASHSCOPE_API_KEY` | 阿里云百炼密钥 |
| `DASHSCOPE_DIARIZE_MODEL` | 说话人分离模型，默认 `qwen-audio-3.1-asr-flash` |
| `DASHSCOPE_DIARIZE` | `0` 可关闭说话人分离 |

**推荐配置**：`ASR_PROVIDER=qwen`，支持原生说话人分离，无需注册声纹。

### 其他可选配置

| 变量 | 说明 |
|---|---|
| **LLM_FIRST_TOKEN_MS** | 会中提问时，模型多久没吐第一个字就切到本地检索兜底，默认 `15000` |
| **LIVE_QA_TIMEOUT_MS** | 会中提问单次生成的总超时，默认 `40000` |
| **LIVE_QA_MEMORY_POOL** | 会中提问参与检索的往期记忆条数上限，默认 `800` |
| `VOICEPRINT_BASE_URL` | 外部声纹识别服务地址（`POST /embed`）。不配则只能手动命名说话人 |
| `EMBEDDING_BASE_URL` | 语义检索服务地址（不配则用本地哈希） |
| `STORAGE_DIR` | 音频文件存储目录，默认 `./storage` |

> **关于声纹**：项目内置的离线声纹特征区分度不足（实测不同人相似度约 0.97），
> 无法可靠识别「这是谁」。所以默认情况下说话人显示为「说话人 A / B / C」，
> 由用户在会议详情页手动命名。配置 `VOICEPRINT_BASE_URL` 指向真实的声纹服务
> （如 ECAPA-TDNN）后，自动识别才会生效。

### 配置自检

填好配置后，可以访问以下接口验证是否生效：

```
GET /api/diag/llm    # 检查大模型连通性
GET /api/diag/asr    # 检查语音识别配置
```

返回 `ok: true` 表示配置正确。

## 技术架构

### 核心设计

**1. 状态机控边界，模型控路径**

整个处理流程分为五个固定阶段：

```
准备 → 压缩 → 抽取 → 复核 → 完成
```

阶段边界由代码强制控制（模型不能跳步），但每个阶段内部**调用哪些工具由模型自主决定**。

这样既有确定性（不会漏掉关键步骤），又保留了灵活性（模型可以按需检索、校验）。

**2. 唯一写入路径**

所有纪要数据只能通过一个函数写入数据库，且强制要求携带来源话轮的 ID。

这样保证了「每条结论都能回溯」不是口号，而是数据结构上的硬约束。

**3. 原始数据永不修改**

转写文字永久保留，摘要和纪要是从原文派生出来的。即使摘要生成有误，原始记录永远可查、可重新生成。

**4. 宁可标未知，也不硬猜**

- 说话人认不出来 → 标记「说话人 A / B / C」，由用户手动命名，而不是按相似度随便套一个名字
- 检索不到相关内容 → 明确回答「没找到」，而不是编造
- 真实服务不可用 → 显示降级提示，而不是静默替换

会议纪要的价值在于可信，不在覆盖率。

## 已知限制

如实列出当前实现的不足之处：

| 限制 | 说明 | 影响 |
|---|---|---|
| **长音频不支持** | 同步识别接口限制单次 5 分钟 | 超过 5 分钟的音频需改用实时模式 |
| **声纹识别不可用** | 离线声纹特征区分度不足（不同人相似度约 0.97），无法自动认出「这是谁」 | 需接入外部声纹服务，或用说话人手动命名 |
| **说话人命名不跨会议** | 手动标注只作用于单场会议 | 每场会议都需重新标注 |
| **语义检索是本地兜底** | 未配置 embedding 服务时使用字符哈希 | 「换个说法」的查询召回率有限 |
| **追问检索范围有限** | 只查「决议」与「记忆」两类，不查转写原话与摘要 | 会上说过但未抽成决议的细节查不到 |
| **会中提问只读已沉淀的记忆** | 往期只召回记忆里已沉淀的结论，不召回往期会议的转写原话 | 想翻上一场会的原话，要去「跨会议追问」或会议详情 |
| **会中提问是单轮** | 每次提问独立，不记得上一个问题 | 追问式对话（「那谁负责？」）需要重复主语 |
| **会中提问靠关键词召回** | 检索是 bigram + 意图词扩展，不是向量检索 | 换个说法的问法可能召回不全，此时会如实回答没找到 |
| **记忆去重较粗** | 按内容完全相等判断重复 | 表述相似但措辞不同的记忆会并存 |
| **检索未感知记忆状态** | 追问时未排除「已过时」「有冲突」的记忆 | 可能返回已被取代的结论 |
| **无密码找回** | 只有登录和注册 | 忘记密码需管理员重置 |
| **无登录限流** | 未限制失败次数 | 生产环境需补充 |
| **实时延迟 1~2 秒** | 受网络与识别服务往返影响 | 非字级实时 |

## 开发说明

### 为什么需要自定义 server

Next.js 的 Route Handler 不支持 WebSocket 升级，而实时转写需要全双工通信。

因此 `server.mjs` 在 Node HTTP server 上挂载了 WebSocketServer，与 Next 共用同一端口。

**启动时请使用 `pnpm start`**（内部调用 `node server.mjs`），不要直接用 `next start`，否则实时功能不可用。

### 添加新的会议类型

在 `lib/skills/` 下新建一个文件，导出 Skill 配置：

```ts
export const mySkill: Skill = {
  id: "my-skill",
  name: "自定义会议类型",
  description: "适用场景说明",
  focus: ["要抽取什么", "关注什么"],
  constraints: ["硬性约束"],
  overviewGuide: "概述怎么写",
  examples: [/* 少样本示例 */],
};
```

然后在 `lib/skills/registry.ts` 中注册即可。
