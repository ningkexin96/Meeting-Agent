## 背景

现在已经有两条链路：

| 链路 | 现状 | 缺口 |
|---|---|---|
| `#26` 实时转写 | 边说边出字，增量抽决议/待办/风险 | 只能「看」，不能「问」 |
| `#16` 跨会议追问 | 检索历史**记忆与决议** | 会议**正在开**的时候没有可用数据；且不查转写原话 |

用户真正需要的是第三种动作：**会开着、话还在说，直接问「刚才说了什么」、「这个需求谁负责」**，
并且立刻得到回答，而不是等会开完、音频传完、点一次「生成纪要」才知道会上讲了什么。

`#16` 和 `#26` 拼起来也满足不了：`#16` 的检索范围是 `memory` 与 `decision`，
而这两张表只有 `saveMinutes()` 之后才有数据 —— 也就是**必须会议结束**。
因此会中问答需要一条独立的、直接读实时转写的过程数据的链路。

## 目标

1. 实时会议页固定一个**提问输入框**，随时可问，不用等会议结束
2. 回答只依据**当前这场会议已经转写出来的内容**（含正在进行中的中间识别结果），回答带出处
3. 答不出来就说「没找到」，**不编造**（与 `#16` 同一底线）
4. 上下文要跟得上会议进度：回答时把最新的转写一起带上，不能只看几秒前的快照
5. 失败可降级：模型不可用时用**本地抽取式回答**兜底，而不是整条链路报错

## 关键设计决策

### 1. 为什么查 `LiveSegment` 而不是 `TranscriptTurn`？

`TranscriptTurn` 只有在 `endSession()` 时才从 `LiveSegment` 合并过去。
会中直接查它只能查到空表。所以问答的取数口径是：

```
LiveSegment（当前会话语义）> TranscriptTurn（历史话轮，兜底）> 空
```

### 2. 为什么必须由前端把最新转写随问题一起发上来？

服务端只读库里的 `LiveSegment` 会"慢半拍"：ASR 最终结果落库 → 前端收到推送 → 用户提问，
中间的**正在识别中（interim）**文字还没有落库。
把这些中间结果作为「正在识别（未定稿）」一并送进上下文，用户问「刚才说了什么」时才能拿到真正最新的内容。
定稿片段永远以数据库为准，前端送来的定稿部分只用来**填补库中缺失的序号**，不会覆盖库里已有的文字。

### 3. 为什么用抽取式兜底而不是"模型不可用就报错"？

会中问答的价值在于「随手一问就有回应」。模型超时或网关抖动时，
用 BM25 式的本地打分从转写里挑出最相关的几句原话直接回答，
用户至少能看到"会上是谁在什么时候说了什么"，比转圈 30 秒后报错好得多。
兜底结果会明确标注「本地检索」，不会伪装成模型生成的结论。

### 4. 本轮不做的

- 多轮对话（当前是单轮问答，与 `#16` 保持一致）
- 语音提问（复用实时识别会把用户自己的提问写进会议转写，需要独立音源，成本高）
- 跨会议混合检索（会中只回答**本场会议**，避免答案串台）

## 验收标准

- [ ] 实时会议页有提问输入框，会议进行中即可提问
- [ ] 问「刚才说了什么」能回答最近的内容，并列出时间与说话人
- [ ] 问一个会里没提到的内容，回答「没找到」，不编造
- [ ] 回答带出处（时间 + 说话人 + 原话），可点开定位
- [ ] 会议刚开始还没有转写时，明确提示「还没有转写内容」
- [ ] 模型不可用时走本地检索兜底，不报错
- [ ] viewer 不能提问（需要 `agent:run` 能力）
- [ ] 跨租户不能读取他人会话（第 3 层隔离）
- [ ] 输入超长、非法 JSON 都返回 400 而不是 500
