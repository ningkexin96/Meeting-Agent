## 背景

会议列表只能新建、不能删除。测完的、讲错的、演示用的会议越积越多，列表全是噪音。

看起来是个小功能，但"删一场会"牵扯到 9 张表，而且其中三处关系**没有配级联删除**，
不处理清楚会留下看不见的脏数据。

## 先说结论：直接删会失败

实测（SQLite）：

```
prisma.meeting.delete({ where: { id } })
→ P2003: Foreign key constraint violated
```

原因是有三条关系没配 `onDelete: Cascade`：

| 关系 | 现状 | 如果不处理 |
|---|---|---|
| `Embedding.meetingId` | 普通字符串列，**没有外键** | 删除后向量索引永远留在库里，检索时会命中"幽灵内容" |
| `Memory.meetingId` | 无级联 | 外键挡住删除，或（若加了级联）误删团队长期知识 |
| `Meeting.audits` | 无级联 | 外键挡住删除 |

`Citation → TranscriptTurn` 虽然有级联，但那是数据库隐式行为，这里也显式删一遍，
让"删了哪些东西"在代码里可读，不依赖具体实现。

## 关键设计决策

### 1. 记忆只解绑，不删除

用户删会议，通常是想清掉"这场会"，不是想把从这场会里学到的结论一并抹掉。
而且记忆已经是独立的长期知识资产（有自己的状态流转：生效/过时/冲突/遗忘）。

所以删除时执行 `memory.updateMany({ meetingId: null })`，并在接口返回里告诉用户
「有 N 条记忆被保留」。界面上会明确写这句话。

### 2. 审计必须留下

谁在什么时候删了哪场会，是必须可查的。但审计记录本身挂在 `meetingId` 上、随会议级联删除。
所以顺序是：**事务内删掉旧审计 → 事务外补写一条 `meeting.deleted`**（不挂 meetingId，只记在 detail 里）。

### 3. 全部在一个事务里

删一半失败会留下残缺数据，比不删更糟。9 张表的删除 + 记忆解绑在一个 `$transaction` 内完成，
超时放宽到 20 秒（转写多的会议删除会慢一些）。

### 4. 音频文件放在事务之后

文件系统操作无法回滚，放进事务会制造"数据库回滚了但文件没了"的不一致。
所以事务成功后才删文件，失败只记日志。
另外做了路径校验：只允许删 `STORAGE_DIR` 内的文件，防止 `audioPath` 被构造成 `../../` 删到别处。

### 5. 权限：只有 owner 能删

member 已经能建会、改纪要，但删除会连带清掉转写、纪要和实时记录，**不可逆**。
一次性判断交给对数据负责的 owner 更合适。新增能力 `meeting:delete`，写进 RBAC 矩阵，
前端用同一个 `canDeleteMeeting()` 决定是否显示入口——规则只有一份。

### 6. 为什么要求输入标题才能确认

会议列表里经常有好几场同名会议（"未命名会议"就一堆）。光点"确定"很容易删错行。
要求把标题打一遍，能把"手滑"挡在门外。用原生 `<dialog>` 实现，
自带焦点陷阱、Esc 关闭和背景遮罩，不用自己搭一层容易出问题的遮罩。

## 踩坑记录

| 坑 | 现象 | 修法 |
|---|---|---|
| 列表整行是链接 | 点删除会跳进会议详情 | 按钮内 `preventDefault` + `stopPropagation` |
| 服务端组件传回调 | 详情页是 Server Component，不能传 `onDeleted` 函数 | 改成 `redirectTo` 字符串，逻辑留在客户端组件里 |
| 删除中途按 Esc | 请求发了一半界面被关掉 | `onCancel` 时若 `busy` 则 `preventDefault` |
| 删除图标不可见 | 只在 hover 时 `opacity-0`，用户根本发现不了功能 | 常态淡灰可见，hover 变红 |

### 最严重的一个：删除后跳到已删会议的 404 页

**现象**：点「永久删除」后，页面跳到 `/meetings/<刚被删掉的 id>`，显示黑底 404。

**定位过程**：在页面里 hook `history.pushState` / `replaceState`，记录每次调用的 URL。
捕获到删除成功后仍然 `pushState` 到那个已删除的会议 id。

**根因**：`<dialog>` 被渲染在删除按钮组件内部，而组件整体嵌在列表的 `<Link>` 里。

1. `doDelete()` 成功后先 `setOpen(false)`，React 重渲染，`<dialog>` 被重新挂载
2. 原生 `<dialog>` 的 **default `open` 属性是 true**，于是它自己又"打开"了一次
3. 这次打开触发 `onCancel` / 冒泡到外层的 `<Link>`，产生一次客户端导航
4. 导航目标是刚被删掉的会议 → 404

**修法（两处，缺一不可）**：

1. **顺序**：先 `dialogRef.current.close()`，再 `router.replace("/")`，不留"已关状态 + 已删路由"的窗口期
2. **结构**：用 `createPortal` 把 `<dialog>` 挂到 `document.body`，彻底脱离 `<Link>` 与整行点击的作用域

**顺带修掉的噪声**：删除瞬间，详情页上挂着的 `/api/meetings/[id]/stream` SSE 仍会请求已删会议，
控制台出现一次 404。新增 `runBus.drop(meetingId)`，在删除前断开该频道订阅。

## 验收标准

- [x] owner 可删除；member / viewer 返回 403
- [x] 未登录 401，不存在 404，跨租户 404
- [x] 删除后：话轮、引用、纪要、决议、摘要、实时会话、实时片段、说话人**全部为 0**
- [x] 删除后：语义索引为 0（最容易漏的一项）
- [x] 删除后：记忆仍存在且 `meetingId` 为 null
- [x] 删除后：写入 `meeting.deleted` 审计，含会议标题与被删明细
- [x] 重复删除返回 404 而不是 500
- [x] 列表与详情页都有入口，二次确认需输入标题

## 不做

- 回收站 / 软删除：会议数据量大且主要由进程产生，真要做需要独立的设计（存储成本、恢复窗口、回收策略），不在本次范围
- 批量删除：先确认单条删除的正确性，批量是纯 UI 扩展，随时可加
