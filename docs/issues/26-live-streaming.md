## 背景

目前只有「会后上传音频 → 整体转写」的离线链路（#22）。会议场景真正的价值在于
**会中就看见**：边说边出转写、边说边积累决议和待办，会议结束时钟已经基本成型。

这是原 backlog #22 的实时分支，本轮落地。

## 方案选型

| 方案 | 结论 |
|---|---|
| A. WebSocket 推音频流，上游直连流式 ASR | ❌ 上游必须支持 WS 协议（FunASR 2pass 等），适配面窄；本地无 ffmpeg 难以处理 webm |
| B. **浏览器分段录音，每段独立上传** | ✅ 任何 ASR 都能用（复用 #22 的适配器）；前端可控制切片长度 |
| C. 先 B，接口按可替换流式后端设计 | ✅ 采纳：抽象 `StreamSession`，将来换 WS 不动前端与抽取逻辑 |

**采用 B + C**：`MediaRecorder` 每 ~4 秒切一片上传，服务端按 session 暂存、
拼接到当前窗口后调 ASR，把新话轮推给前端；同时按窗口做增量纪要抽取。

## 目标

1. 浏览器录音 → 每片上传 → 服务端转写 → **新话轮实时推到前端**
2. **增量纪要**：每积累 N 个新话轮或 T 秒，就对窗口内新增内容抽一次决议/待办/风险
3. 会议结束 → 合并成最终纪要，走既有的 `saveMinutes` 唯一写库路径
4. 失败可恢复：某片 ASR 失败不阻断整场，标记该片待复核

## 关键设计决策

**为什么按「窗口」抽增量，而不是每次全量重抽？**
全量重抽会：① 成本随会议时长线性涨；② 同一决议被反复抽取导致重复条目。
按窗口只抽新增部分，再按文本相似度去重，是成本与质量的最优解。

**为什么增量结果不直接落 `Minutes` 表？**
`Minutes` 是权威数据源，只允许 `saveMinutes()` 写一次成型的结果。
增量内容先落 `LiveSegment`（过程数据），会议结束时合并成最终纪要。
这样保持「模型不能直接写权威库」这条底线不被实时功能破坏。

**切片长度为什么是 4 秒？**
太短：请求过多且上下文断裂，ASR 质量差；
太长：延迟明显，失去「实时」意义。
4 秒是压测后的折中（见 `scripts/test-stream.ts` 中的延迟断言）。

## 验收标准

- [ ] 创建实时会话，返回 sessionId
- [ ] 分片上传后可取回该会话的累计话轮
- [ ] 新话轮通过 SSE 推送到前端，且按顺序、不重复
- [ ] 每 N 个新话轮触发一次增量抽取
- [ ] 增量结果按内容去重，不产生重复条目
- [ ] 结束会话后合并成最终纪要，引用可回溯到具体话轮
- [ ] 单片 ASR 失败不阻断会话，标记待复核
- [ ] viewer 不能开启实时会话（RBAC）
- [ ] 跨租户不能读取他人 session（第 3 层隔离）

## 不做

- 真正的 WebSocket 音频流（接口已预留）
- 说话人实时识别（声纹按整场结束后算，实时聚类抖动太大）
- 实时字幕级（词级）时间对齐
