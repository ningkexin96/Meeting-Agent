## 背景

原实现把 ASR 的 `speaker_0/1/2` 按顺序映射到预置参会者，这对演示够用，但**真实会议里
根本不知道谁是谁**。上一轮 `#23` 记的是 backlog，本轮落地。

## 目标

- 声纹库：注册 / 重复注册取质心 / 删除 / 列表
- 聚类：按余弦相似度 + 阈值判定，**不预设簇数**（一个会议里几个人说话事先不知道）
- 认不出就标「未知参会者」+ `needs_review`，**绝不硬猜**

## 关键设计决策

**为什么不用 k-means？**
k-means 需要预设簇数 k，而「这场会几个人说话」恰恰是未知量。
用「余弦 + 阈值」的单遍聚类，天然支持 1 人会议到 N 人会议。

**为什么认不出要标未知，而不是挑最像的？**
挑最像的等于在说话人归属上制造幻觉。会议纪要的价值在于可信，
一条「可能是张伟说的」比「未知」更有害。

**为什么重复注册取质心而不是覆盖？**
单次注册受录音质量影响大；质心随样本增多而收敛，是声纹系统常规做法。

## 验收标准

- [x] 无人脸库时，同一人的多个片段聚成同一簇
- [x] 按发言量排序，主讲人排前面
- [x] 有声纹库时能认领身份并给置信度
- [x] 声纹库外的人保持未知 + 待复核
- [x] ASR 把同一人拆成两个标签时能合并
- [x] 空输入 / 单人会议不崩
- [x] 重复注册样本数递增、向量取质心
- [x] 维度不一致时报错（不静默写脏数据）
- [x] viewer 不能注册声纹（403）
- [x] 小于 1KB 的音频被拒（400）
- [x] 跨租户不可读（第 3 层隔离）

## 踩坑记录

**`centroid([...JSON.parse(existing.embedding), embedding])` 是错的。**
`JSON.parse` 返回的是「一个向量」，展开后变成一堆数字，不是「向量的数组」。
正确写法：`centroid([prev, normalize(new)])`，并且要校验维度一致。

**没有声纹服务时怎么办？**
提供 `deterministicEmbedder`：按音频字节 + 时间窗算稳定伪向量。
它不是真声纹（不能跨设备复用），但能让「上传 → 提取 → 聚类 → 标待复核」整条链路离线验证。

## 不做

- 跨设备声纹（需要真实声纹模型）
- 声纹活体检测
- 实时声纹（会议中即时识别）
