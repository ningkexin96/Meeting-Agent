## 背景

`#27` / `#28` 的会中提问已经能用，但回答是**一次性返回**的：

```
用户提问 → 空白等待 → 整段答案突然出现
```

实测首字要 2~3 秒，稍复杂的问题要更久。会中场景里用户体验很糟：

1. 用户不知道系统是在思考、卡住了，还是根本没收到请求
2. 想中途换问题时没有任何反馈，只能干等
3. 模型偶尔返回空内容，用户等了好几秒才看到"模型不可用"

## 目标

1. 首字尽快出现，后续增量逐块渲染
2. **出处先于答案**：先告诉用户"依据是哪几句"，再开始写答案
3. 用户可以中途取消，取消时上游模型连接必须真的断开
4. 上游卡住时要有明确反馈，而不是让光标一直转

## 关键设计决策

### 1. 为什么用 SSE 而不是 WebSocket

- 这是一问一答的单向推送，不需要全双工
- 项目里已有两处 SSE 先例（`/api/meetings/[id]/stream`、`/api/live/[id]/stream`），
  包括 15 秒心跳防止代理层掐断空闲连接，直接沿用同一套写法
- EventSource 不支持 POST，所以用 `fetch` + `ReadableStream` 手动切帧，
  换来的是**可以取消**（`AbortController`）

### 2. 为什么把「准备」和「生成」拆开

`prepareQuestion()` 负责鉴权、检索、拼上下文，**不调模型**，几百毫秒内完成；
`streamAnswer()` 才把上下文交给模型。

拆开以后，`meta` 事件（出处 + 往期记忆）可以在模型开口**之前**就推给前端。
这个顺序很重要：用户看到"依据已找到 6 处"就知道系统在工作，而不是对着空白猜。

### 3. 为什么不用 pi-agent-core 的流，而是直接用 streamSimple

会中问答的这条链路本来就没有经过 Agent 的完整运行时，只是「拼好提示词 → 调模型」。
直接用 `streamSimple` 拿 `text_delta`，少一层抽象，也少一层难以排查的时序问题。

### 4. 三重熔断

只靠整体超时不够，实测有两种"假死"要分别处理：

| 情况 | 表现 | 处理 |
|---|---|---|
| 上游迟迟不开始吐字 | 光标一直闪 | `LLM_FIRST_TOKEN_MS`（默认 15s）首字超时 |
| 整体跑太久 | 一路吐字但停不下来 | `LIVE_QA_TIMEOUT_MS`（默认 40s）整体超时 |
| 用户主动取消 | 立刻想打断 | `AbortController`，客户端断开即中止上游 |

任一情况都**不是报错结束**：回落到本地检索，把相关原话列出来。

### 5. 取消不写审计

用户点「停止」是自己的选择，不是系统故障。如果也记一条"模型失败"，
审计里会堆满噪声，以后排查真实故障就会被淹没。所以取消走单独分支，直接结束。

### 6. 为什么保留非流式入口

`answerLiveQuestion()` 内部就是「准备 + 跑完整个流」，
测试脚本、诊断工具、将来的批量调用方只需要一个 Promise。两条路复用同一套逻辑，
不存在"流式修了、非流式没修"的分叉。

## 踩坑记录

| 坑 | 现象 | 修法 |
|---|---|---|
| 反引号冲突 | 在 `page.evaluate` 里写模板字符串，外层 shell 转义把脚本改坏了 | 探针脚本改成数组 join / 独立常量，不嵌套反引号 |
| 收尾不关流 | 正常结束后上游连接仍挂着，模型继续计费 | `finally` 里无条件 `abort()` |
| 空内容误判 | 上游只发 `done` 不发 `text_delta` 时文本为空 | 从 `partial.content` 兜底取一次全文 |

## 验收标准

- [x] 响应头为 `text/event-stream`，且 `X-Accel-Buffering: no`（防止代理缓冲）
- [x] `meta` 事件先于任何 `delta` 到达
- [x] 答案分多块到达，不是一次性吐出
- [x] 界面上的答案文本长度随时间递增（逐字渲染）
- [x] 生成中按钮变为「停止」，点击后立即停止且不产生审计噪声
- [x] 客户端断开时上游模型连接被中止
- [x] 模型失败/超时/空内容时仍返回可用答案（本地检索兜底）
- [x] 准备阶段错误（401/403/404/400）仍以普通 JSON + 正确状态码返回

## 不做

- 思考过程（reasoning）的流式展示：当前模型不开启推理，且会中用户只需要结论
- 断线续传：答案是一次性的，重连没有意义，重问即可
